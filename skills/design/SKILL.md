# Design

A glass-box design method. Every visual choice traces to a **lever** (a named setting you can turn), every quality
claim to a **check** (a script that measures, or a named judgment), and every "done" to evidence in the message.
Explain choices in plain words first, then the technical term. The person may be a designer, not a coder.

Paths below are relative to this skill's folder.

## What runs here

| Tool | What it does | How |
|---|---|---|
| `engine/levers.mjs` | turns lever settings into DTCG design tokens (light, dark, high contrast), colour from HCT tonal palettes | `node engine/levers.mjs --set colour.seed=#3b5bdb --set type.ratio=1.25 --tokens > tokens.json`; `--explain <lever>`; `--check`; `--settings settings.json` |
| `engine/contrast.mjs` | WCAG 2.2 contrast of every token pair in every theme x contrast mode | `node engine/contrast.mjs tokens.json` (exit 0 pass, 1 fail, 2 error) |

Both need only Node (no packages, no browser). If you can run code, run them and paste the output. If you cannot,
say so, compute contrast by hand for the key pairs (body text, muted text, accent button text, focus ring), and label
the result Inferred. The references sometimes name browser instruments (`inspect`, `capture`, `states`, `bench`,
`board`, `lint`) from the full Claude Code harness. They do not exist here. Do the same check by eye on a rendered
artifact or screenshot, and label it Inferred.

## 1. Depth

Choose depth from the change surface (owners, shared tokens, sibling screens, open questions), not from how long
the request is. Say it in one line first: "Depth: focused. One surface (pricing page): brief, idea gate, levers, review."

| Signal | Depth | Steps |
|---|---|---|
| One property or component in an accepted system; known answer | `direct` | craft-floor + the checks for what changed |
| One surface with a known job: a new page, a rejected look, a shared component, a token change | `focused` | + brief, idea gate, levers + tokens, review |
| Open identity, several surfaces, a new design system, or the person wants options | `portfolio` | + up to 3 directions side by side, states for every component |

Escalate when you find a shared contract or a floor you cannot fix locally. Details: `references/depth.md`.

**Surface.** Decide per screen: `marketing` (persuades: landing, pricing, campaign) or `app` (operates: dashboard,
settings, editor). Marketing earns hero-scale type and one strong focal point. App screens earn density, calm
titles (h1 at most about 34 px, 28 px on a phone), tabular numbers and visible states.

## 2. Brief and idea gate

Before any visual choice, write or read the contract (`contracts/` has the shapes):

- **PRODUCT.md**: who it is for, the job of each surface, surface type, constraints, the real copy and data.
- **DESIGN.md**: the direction in prose, the identity carrier, lever settings with reasons, forbidden drift.
- **tokens.json**: DTCG tokens; generated by `engine/levers.mjs`, never hand-invented.
- **states.json**: required interaction states per component (`contracts/states.example.json`).

Then pass the idea gate (`references/idea-gate.md`): one sentence saying what this design is about, one **live
thing** (the single element that makes it this product and not a template), and the **competitor test** (would a
rival's logo fit on it unchanged? If yes, it has no identity yet). Removing generic tells is not a design.

## 3. Direction (focused and portfolio)

Play the **art-director** (`roles/art-director.md`): up to three directions, each as

- lever settings changed from default, with a why per lever (`node engine/levers.mjs --explain <lever>`),
- 1-3 **seeds** blended from `knowledge/seeds/<brand>/DESIGN.md` and `tokens.json` (74 real brand systems),
  taking one named property from each (type voice from one, colour logic from another). Never copy a seed whole;
  record which seed gave which property,
- the live thing and the competitor test.

Show them side by side when you can render (an HTML artifact with the three directions as panels). Let the person
choose. The art-direction gate (`references/art-direction-gate.md`) covers identity and rejected looks.

**Images as the vibe.** When the person gives images, look at them and name what you see: 3-6 dominant colours
with rough hex values, the light/dark balance, warm or cool, saturation, contrast, texture (glow, grain, gradient),
and the mood in plain words. Map that onto levers (seed colour, accent tone, dark-surface tone, radius, density,
type ratio, motion) and say which image drove each choice. Label colour readings Inferred: you are estimating by eye.
Only read the images the person gave.

## 4. Levers, dials and tokens

Levers are in `knowledge/levers.json` (14: type base, ratio and leading; space unit and density; radius; colour seed, accent tone, neutral tint,
contrast and dark tones; motion duration and easing). A **dial** (`knowledge/dials.json`: calmer, louder, denser, airier, softer,
sharper, quicker, slower) is a shortcut that moves several levers. Always report which levers it moved, from and to.

Never say "the headings feel cramped" alone. Say the lever and its value: "type.ratio is 1.125, so 16 px body and
18 px h4 read as one size; 1.25 separates them". If no lever covers it, name the CSS property and say so.

Play the **systems-designer** (`roles/systems-designer.md`) to turn the chosen direction into settings, generate
tokens, run contrast, and write states.json. A value you need that is not in tokens.json is a lever change, never a
literal in code.

## 5. Build

Load the **craft-floor** skill before writing interface code. Use only tokens (as CSS custom properties). Build with
real content at real lengths. Design the empty, loading, error and long-content states, not just the happy path.

## 6. Review and verdict

Play the **reviewer** (`roles/reviewer.md`) in a fresh frame of mind: judge only the rendered result, the brief
and the check output, not your intentions. Use `references/critique.md` and the tells in `knowledge/tells.json`
(devices that read as machine-made). Return one verdict:

- **KEEP**: every check passes and the direction holds.
- **REVISE**: fixable problems; any unwaived failure caps the verdict here. A contrast failure cannot be waived.
- **REJECT**: the direction itself fails (not a count of findings).
- **UNKNOWN**: a check could not run or the result could not be seen.

At most five evidence items, each citing what was seen and a rule or tell id, plus the single most important fix.

## Glass box

- **Terms.** The first time a term from `knowledge/glossary.json` appears, define it in one plain sentence.
- **Why-panels.** Explain a lever, check or finding in three parts: plain words, the technical term or formula,
  and a pass/fail example. Source the text from `knowledge/levers.json`, `knowledge/rule-notes.json` and the
  glossary, never from memory; if a why is missing, say so. Details: `references/glass-box.md`.
- **Evidence labels.** Mark claims Observed (a script or screenshot shows it), Derived (follows from observed
  values), Inferred (judgment, or estimated by eye) or Unknown. Never present an Inferred claim as measured.
